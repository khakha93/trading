# Refactor Plan

## 목표
- 앱의 진입점과 UI 로직을 분리해 유지보수를 쉽게 만든다.
- 초기 로딩 자동 검색 문제를 포함한 상태 흐름을 명확하게 만든다.
- 테스트 가능하고 확장 가능한 구조로 정리한다.

## 현재 문제
- [app.py](../app.py)가 UI, 상태 관리, 데이터 호출, 차트 생성, 스타일 정의까지 모두 담당하고 있다.
- 세션 상태 초기화가 중복되고, 흐름이 분산되어 있다.
- 검색/초기 로딩/차트 계산이 한 파일 안에 섞여 있어 변경 시 영향 범위가 크다.
- 기능 추가나 디버깅 시 회귀 위험이 높다.

## 리팩토링 원칙
- 기능은 유지하되 책임을 분리한다.
- UI와 비즈니스 로직을 분리한다.
- 상태 변경은 한 곳에서 관리한다.
- 작은 함수/모듈로 나누어 테스트 가능하게 만든다.

## 1단계: 구조 분리
### 목표
앱 진입점을 가볍게 유지하고, 화면 로직을 작은 단위로 나눈다.

### 작업
- [app.py](../app.py)에서 앱 레이아웃 렌더링을 함수 단위로 분리한다.
- 사이드바 UI, 검색 탭 UI, 분석 탭 UI를 각각 함수로 분리한다.
- 앱 초기화를 담당하는 함수 `initialize_app()`를 만든다.

### 예상 결과
- 진입점이 단순해지고, 각 기능이 독립적으로 읽힌다.

## 2단계: 상태 관리 정리
### 목표
세션 상태 키를 명확히 하고, 초기값 설정을 한 곳으로 모은다.

### 작업
- 세션 상태 초기화 로직을 `initialize_session_state()`로 통합한다.
- 검색어, 바스켓, 가격, 마스터 다운로드 상태 같은 상태를 명시적으로 관리한다.
- 자동 검색 여부는 별도 함수로 판별한다.

### 예상 결과
- 상태 관련 버그를 찾기 쉬워진다.
- rerun 시 예측 가능한 동작이 된다.

## 3단계: 데이터/서비스 계층 분리
### 목표
UI에서 API 호출/파일 다운로드/계산 로직이 직접 섞이지 않도록 한다.

### 작업
- 검색 로직, 포트폴리오 조회 로직, 옵션 가격 조회 로직을 서비스 함수로 분리한다.
- [src/master.py](../src/master.py), [src/kis_client.py](../src/kis_client.py), [src/pricing.py](../src/pricing.py) 활용 방식을 UI에서 단순화한다.

### 예상 결과
- UI 변화와 데이터 로직이 분리된다.
- 테스트 가능한 함수가 늘어난다.

## 4단계: 차트/표시 로직 분리
### 목표
차트 그리기와 분석 계산을 분리한다.

### 작업
- Plotly 차트 생성 로직을 별도 함수로 만든다.
- 수익곡선 계산과 시나리오 분석 계산을 별도 함수로 분리한다.

### 예상 결과
- 차트 변경이 분석 로직에 영향을 덜 준다.
- 미래에 다른 시각화 방식으로 바꾸기 쉬워진다.

## 5단계: 스타일 분리
### 목표
CSS/HTML 스타일을 코드 로직과 분리한다.

### 작업
- 스타일 문자열을 별도 상수나 모듈로 옮긴다.
- 반복되는 마크업을 템플릿 함수로 정리한다.

### 예상 결과
- UI 변경이 쉬워지고, 파일이 덜 복잡해진다.

## 6단계: 테스트 추가
### 목표
중요 흐름을 자동으로 검증한다.

### 작업
- 초기화 로직 테스트
- 검색 조건 테스트
- 바스켓 추가/삭제 테스트
- 마스터 파일 부재 시 동작 테스트

### 예상 결과
- 리팩토링 중 회귀를 잡을 수 있다.

## 권장 실행 순서
1. 세션 상태 초기화 정리
2. 앱 렌더링 함수 분리
3. 검색/초기 로딩 로직 분리
4. 차트/분석 로직 분리
5. 스타일 분리
6. 테스트 추가

## 리스크 관리
- 한 번에 모든 파일을 바꾸지 않는다.
- 기능 동작은 유지하면서 작은 단계로 진행한다.
- 각 단계마다 앱이 정상 동작하는지 확인한다.
